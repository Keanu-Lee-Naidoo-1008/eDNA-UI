# Design brief: eDNA Web Portal

Use this brief to design or redesign screens for the eDNA Web Portal. Read all of it before producing anything. Section 6 covers how to avoid the "generated by AI" look, and it matters as much as the colour tokens.

---

## 1. What the product is

The eDNA Web Portal is an identity and biometric enrolment system for government departments in South Africa. The first customer is a provincial treasury. The portal registers staff and gives them a verified digital identity. That identity lets them sign in, sign transactions and get access to financial systems such as the national "transversal" systems (BAS, PERSAL, LOGIS).

The portal handles:

| Module | What happens there |
|---|---|
| **Logon** | Operators sign in with a fingerprint or their face. Passwords are not the main path. |
| **User Enrolment** (4-step wizard) | 1. User details. 2. Biometrics: fingerprints and/or face. 3. Transversal accounts. 4. PKI certificate and smartcard. |
| **Biometric Enrolment** | Capture 4 different fingers, 2 samples each, from a USB scanner. The operator verifies them, picks a default finger and signs to continue. Missing fingers and hands are handled as exceptions. |
| **Facial Enrolment** | 3 face images, captured in a separate desktop "Facial Capture" app and returned to the portal with a quality score. |
| **User Management** / **Bulk Import** | Search, edit, deactivate users; import users from a file. |
| **Entity Management** | The organisation tree: departments, branches, offices. |
| **Transversal Management** | Link users to their accounts on external government systems. |
| **PKI Enrolment** / **Certificate Management** / **Smartcard Management** | Issue, renew and revoke certificates; issue smartcards and handle them when lost. |
| **Forensic Reports** | Request a signed evidence report on a transaction. An approver reviews a watermarked DRAFT PDF, then signs and forwards it. Legal weight; mistakes are costly. |
| **Audit / System / Headcount Reports** | Who did what and when; how many staff are enrolled per entity. |
| **Update Manager** | Push client software updates to enrolment workstations, grouped by computer group. |
| **System Status**, **My Profile**, **Help** | Health of the capture services, the operator's own details, training videos. |

### Who uses it

- **Enrolment operators.** They sit at a desk with a fingerprint scanner and a webcam and enrol many people in one sitting. They work fast, use the keyboard and want the next action to be obvious. The person being enrolled is often sitting across the desk and can see the screen.
- **Supervisors and administrators.** They manage entities, approve exceptions, run reports and push updates.
- **Approvers.** They review forensic reports. They need calm, careful, readable screens with no ambiguity about what they are signing.

### Where it runs

- Windows desktops at enrolment stations, usually 1366×768 to 1920×1080, sometimes under bright office lighting. A dark mode matters for long sessions.
- A local desktop capture service talks to the scanner and camera. The status bar at the bottom shows whether it is connected.
- Sessions time out, with a visible countdown modal.
- The look should feel like a government-grade system of record: trustworthy, precise, quiet. It should not look like a consumer app or a startup landing page.

## 2. Technical constraints (non-negotiable)

- **Stack:** ASP.NET MVC 5 Razor views (`.cshtml`), **Bootstrap 3.4**, jQuery. Do not introduce React, Tailwind or a new CSS framework.
- **All styling lives in one file:** `Views/Shared/_ModernTheme.cshtml`. It loads after Bootstrap and Site.css and overrides them. Every colour, size and radius is a CSS custom property (`--ed-*`) in that file's colour blocks. No new colours in rules or inline styles.
- **Do not break hooks.** Element `id`s, `name`s, `onclick` handlers, `data-*` attributes and classes used by scripts must survive. `node tools/hookcheck.js compare Views tools/baseline.json` must pass. Adding wrappers and classes is fine; renaming or removing is not.
- **Capture images keep their inline `border-color`.** The capture scripts recolour the border to show finger status. Style around that; never override it.
- **Razor:** CSS at-rules are written `@@media` / `@@keyframes` inside `.cshtml`.
- **Icons:** Bootstrap 3 Glyphicons Halflings (`glyphicon glyphicon-*`). Add small inline SVGs (stroke, `currentColor`) only where Glyphicons has nothing suitable, e.g. sun/moon, fingerprint, face.
- **Preview:** `preview/template.html` is a static mock of the main screens. `node preview/build.js Views` injects the real theme into `preview/preview.html`. Keep the preview in step with the views.

## 3. Colour system

Two modes. Light is the default. Dark mode follows the OS setting, and `<html data-theme="light|dark">` overrides it. The **Theme** button in the top bar sets that attribute and saves the choice to `localStorage` under the key `ed-theme`.

### Light mode: blue / white

| Token | Hex | Used for |
|---|---|---|
| `--ed-bg` | `#F4F7FB` | Page background |
| `--ed-surface` | `#FFFFFF` | Panels, cards, modals, top bar |
| `--ed-surface-2` | `#EEF3FA` | Raised: finger tiles, inputs, hover states |
| `--ed-border` | `#DAE3EF` | Card and input borders, dividers, empty stepper bars |
| `--ed-text` | `#0C1B33` | Headings and body text |
| `--ed-text-muted` | `#5A6A84` | Labels, meta info, placeholders |
| `--ed-primary` | `#1E5BD8` | Primary buttons, links, active step, live finger, face ring |
| `--ed-primary-hover` | `#174AB3` | Hover on primary buttons and links |
| `--ed-on-accent` | `#FFFFFF` | Text on blue buttons |
| `--ed-primary-soft` | `#1E5BD8` at 8% | Background of the selected or live tile |
| `--ed-success` | `#14996F` | Ticks, "captured", pass states |
| `--ed-warning` | `#B97A0A` | Low quality scores, queued or pending |
| `--ed-danger` | `#D23B3B` | Errors, failed capture, clear/delete |

### Dark mode: navy / turquoise

| Token | Hex | Used for |
|---|---|---|
| `--ed-bg` | `#0A0F1C` | Page background |
| `--ed-surface` | `#111A2B` | Panels, cards, modals, top bar |
| `--ed-surface-2` | `#16213A` | Raised: finger tiles, inputs, hover states |
| `--ed-border` | `#22304A` | Card and input borders, dividers, empty stepper bars |
| `--ed-text` | `#E7EEF8` | Headings and body text |
| `--ed-text-muted` | `#8C9AB2` | Labels, meta info, placeholders |
| `--ed-primary` | `#5EE6D0` | Primary buttons, links, active step, live finger, face ring |
| `--ed-primary-hover` | `#7BEFDC` | Hover on primary buttons and links |
| `--ed-on-accent` | `#04201C` | Text on turquoise buttons (never white) |
| `--ed-primary-soft` | `#5EE6D0` at 12% | Background of the selected or live tile |
| `--ed-success` | `#5EE6D0` | Ticks, "captured", pass states |
| `--ed-warning` | `#F2B544` | Low quality scores, queued or pending |
| `--ed-danger` | `#F06C6C` | Errors, failed capture, clear/delete |

Supporting tokens: `--ed-*-soft` tints for status backgrounds, `--ed-focus-ring`, `--ed-overlay` (busy screen), `--ed-logo-bg` (white chip behind the logo in dark mode) and `--ed-shadow-rgb`.

**Rules**
- In dark mode, success and accent are the same turquoise. Never rely on colour alone to tell "captured" from "selected". Add a tick, a label or a shape.
- Status always pairs colour with text or an icon: "Captured ✓", "Quality 42 · Low", "Queued". Users may be colour-blind, and the screen may be glanced at from across a desk.
- The capture scripts still use legacy finger-status colours on image borders: not captured `#9FD3F0`, captured `#FFE14D`, verified `#53EA1A`, default finger `#FF1800`. The legend must match whatever the scripts paint. If you propose remapping these to the palette, list the script changes needed. Don't change the legend alone.

## 4. Type, space, shape

| | Value |
|---|---|
| Font | `Segoe UI`, then system-ui. The machines are Windows, so it renders crisply and needs no download. Monospace: Consolas / Cascadia Mono, for IDs, hashes, the clock and certificate serials. |
| Sizes | 13 (meta, table heads) · 15 (body) · 18 (card titles) · 22 (page titles) · 28 (rare). |
| Numbers | `font-variant-numeric: tabular-nums` for scores, counts, IDs and timers. |
| Spacing | 4 · 8 · 12 · 16 · 24 · 32 px. |
| Radius | 6 (inputs, buttons, tiles) · 10 (cards) · 14 (modals). |
| Shell | 64 px top bar · 40 px fixed status bar · content max-width 1320 px. |
| Elevation | Mostly hairline borders. Shadows are faint and reserved for things that float: dropdowns, modals, the sticky action bar. |

### Shell anatomy
1. **Top bar** (surface colour): logo, current page title, then on the right the Theme toggle, Override Default Finger (only when relevant), Help & Support menu and user menu.
2. **Breadcrumb** row with a Close link, or during enrolment the **wizard bar**: "User enrolment" label, "You are enrolling User ID n, Name …" and the 4-step stepper.
3. **Main content**.
4. **Sticky action bar** at the bottom of task pages: Cancel on the left, the next step on the right.
5. **Status bar**: capture service connection, the latest system message, version and clock.

## 5. Key screens and what they must get right

- **Logon:** two large actions, Fingerprint Login and Face Login. Show the service state ("Waiting for the capture service…") rather than marketing copy.
- **Search user:** search field type (eDNA ID / ID number / surname), then a results table. Create New User is visible but secondary to search.
- **User details:** two cards, User Information and User Attributes (Persal number, department, contact). Read-only fields look read-only.
- **Fingerprint enrolment:** left and right hand diagrams with numbered fingers (clickable image maps, fixed at 256×266 px). Below them, 10 finger tiles, each with 2 sample thumbnails and a quality score. The side panel has Exceptions (disable hand), Functions (verify all, set default finger, reset, override) and a colour legend. The **live** finger, the one the scanner is waiting for, must be unmistakable: accent ring plus accent tint plus a label such as "Place finger now".
- **Facial enrolment:** 3 image slots with a quality line under each; buttons for Capture Face Images and Reset; a short 3-step checklist.
- **Forensic review:** a DRAFT warning, a link to open the watermarked preview, a confirmation checkbox the approver must tick, then Approve. Feel deliberate; nothing should be one accidental click away.
- **Modals:** message box, session countdown (big tabular timer in a ring), user info, report error, menu style chooser.

## 6. Make it look designed by people who know the job, not by AI

The palette, navy with turquoise, rounded cards and soft tints, is close to the default "AI dashboard" look. The structure, copy and details are what make it feel built for this job. Apply these:

### Layout
- **Not everything is a card.** Use cards for things that are objects: a user, a finger, a certificate. Settings and form sections can be plain regions split by a rule and a heading. A page made of nested rounded boxes is the biggest giveaway.
- **Density over air.** Operators enrol dozens of people a day. Tables use 36–40 px rows, not 64. Show more rows, not bigger padding.
- **Asymmetric, task-shaped layouts.** The fingerprint screen is hands on the left, tools on the right. The search screen is a bar plus a table. Avoid the default grid of three equal feature tiles with an icon on top.
- **Left-align almost everything.** Centre only the logon card and the countdown timer.
- **Real alignment.** Labels, inputs and table columns line up on a shared grid across cards. Numbers are right-aligned in tables.

### Colour
- **Ration the accent.** One filled accent button per screen: the step that moves the job forward. Everything else is outline, plain text or neutral. Turquoise everywhere reads as generated.
- **No gradients, glows, glassmorphism or coloured shadows.** Flat surfaces and hairlines.
- **Neutrals do most of the work.** The screen should look nearly grey-scale until something needs attention.

### Shape and detail
- **Smaller radii.** Consider dropping cards to 6–8 px and buttons to 4 px. Big pill shapes look generic; tighter corners feel more like a precise tool.
- **Rules instead of shadows** to separate content.
- **One icon set, used sparingly.** Icons on actions that need them (Capture, Verify, Clear), not decoration beside every heading. No emoji.
- **Uppercase labels sparingly.** One level of small-caps label (table heads, side-panel sections) is enough. Don't put an uppercase label above every heading.

### Copy (this matters more than visuals)
- **Use the domain's own words:** eDNA ID, Persal number, entity, transversal account, default finger, sample, quality score, revoke, issue. Not "profile", "workspace" or "insights".
- **Drop cheerful filler.** "Welcome To The eDNA Web Portal. Logon To Explore The Features !" becomes "Sign in with your fingerprint or face." Empty states say what to do: "No fingers captured yet. Click a finger on the hand to start."
- **Sentence case** for buttons and headings ("Sign and continue", not "Sign And Continue"). Check whether IDs or scripts read button text before changing it.
- **Specific numbers and states:** "2 of 4 fingers captured", "Quality 38 (minimum 50)", "Session ends in 01:42".

### Behaviour that signals craft
- **Keyboard first:** visible focus rings, Enter to continue, Esc to close modals, a logical tab order through the finger tiles.
- **State changes are calm and immediate.** A capture landing in a tile switches state with no bounce or confetti; at most a 150 ms fade. Respect `prefers-reduced-motion`.
- **Show system truth.** If the capture service is disconnected, say so in the status bar and disable capture actions with a reason, rather than letting clicks fail silently.
- **Printable reports.** Report and forensic pages get a clean print stylesheet: no shell, black on white, page numbers.

### Details worth adding
- Proper sun and moon SVGs for the theme toggle, replacing the Glyphicon stand-ins.
- A small connection dot with text next to the status bar message ("Capture service · connected").
- Finger numbering that follows the ISO/ANSI finger positions (1 = right thumb … 10 = left little). Check this against the hand images and the capture scripts before relabelling.
- Real hand illustrations with clear hit areas, not stock icons.
- A monospace treatment for eDNA IDs, certificate serials and SHA-256 hashes, with a copy button on hashes.

## 7. What to deliver

For each screen you touch:
1. The updated `.cshtml` markup (hooks intact) and any new rules for `_ModernTheme.cshtml`, using only `--ed-*` tokens.
2. Matching changes to `preview/template.html`, then rebuild with `node preview/build.js Views`.
3. A short note listing every class, ID or text string that scripts might depend on and that you deliberately kept.

### Acceptance checklist
- [ ] `node tools/hookcheck.js compare Views tools/baseline.json` passes.
- [ ] The screen looks right in **both** light and dark mode (toggle in the top bar).
- [ ] No hex colours outside the two colour blocks in `_ModernTheme.cshtml`.
- [ ] Text contrast meets WCAG AA (4.5:1 for body text, 3:1 for large text and UI borders that carry meaning).
- [ ] Every status uses colour plus text or an icon.
- [ ] At most one filled accent button per screen.
- [ ] Works at 1366×768 without horizontal scrolling. The sticky action bar never covers the last field.
- [ ] Copy uses the product's own terms and sentence case, with no filler.
